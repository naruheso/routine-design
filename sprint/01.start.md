### 📋 経費精算システム ヒアリング

**1. 利用シーンと規模について**
- この経費精算システムは社内向けWebアプリケーションを想定していますか？
- おおよその利用人数（社員数・承認者数）は？

**2. 経費データの入力項目について**
- 想定している入力項目を教えてください。例えば：
  - 日付、勘定科目、金額、摘要（メモ）、領収書画像 など
  - 他に必要な項目はありますか？

**3. 承認フローについて**
- 承認者は1名のみですか？それとも複数段階の承認（例：上長→経費担当→経理部長）が必要ですか？
- 「差し戻し」と「否認」の違いについて：
  - **差し戻し** → 修正して再申請可能
  - **否認** → 完全に却下（再申請不可）
  - この認識で合っていますか？

**4. 集計画面について**
- 月別の社員別合計金額のほか、勘定科目別の内訳なども必要ですか？
- 集計データのCSVエクスポートなどは必要ですか？

**5. 技術スタックの指定はありますか？**
- ドキュメントのみの作成でしょうか、それとも後続で実装も予定していますか？
- 実装する場合、使いたい技術（フレームワーク等）の希望はありますか？

### 設計書の構成

| セクション | 内容 |
|-----------|------|
| **1. ドメインモデル全体図** | Mermaidクラス図で4エンティティの関係を可視化 |
| **2. エンティティ定義** | `User` / `Expense` / `ApprovalHistory` / `Category` の全フィールドと責務 |
| **3. 値オブジェクト定義** | `Money`・`ExpenseDate`・`Email` など、バリデーションを内包する型一覧 |
| **4. 列挙型（Enum）定義** | `UserRole` / `ExpenseStatus` / `ApprovalAction` の全パターン |
| **5. ステータス遷移図** | `submit()` / `approve()` 等のメソッド名付きの状態遷移 |

| **7. ドメインサービス定義** | `ApprovalService` / `ReportService` の責務とメソッド |
| **8. ビジネスルール一覧** | BR-01〜BR-09 の実装場所まで明示 |
| **9. リポジトリインターフェース定義** | 各エンティティのリポジトリのI/Fを定義 |

### 設計のポイント

- **`Expense` を集約ルート**として、ステータス遷移ロジックを自身で管理する設計にしました
- **`ApprovalHistory` を不変エンティティ**（一度作ったら変更しない監査ログ）として位置づけました
- **`actorRole` をスナップショットとして保持**することで、ユーザーのロール変更後も履歴の正確性を担保します
- ビジネスルール（BR-01〜09）を全て、どのエンティティ・値オブジェクト・サービスで実装するかまで紐付けました
