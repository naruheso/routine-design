# 承認フロー運用方針

## 概要

本ドキュメントは、経費申請などの承認プロセスにおいて、申請者が同時に承認者になる場合の運用ルールを定めています。

## 現状の問題

上長が経費申請した際に、最初の承認者が自分自身になり、自己承認しようとすると以下のエラーが表示される：

```
自分の申請は承認できません: forbidden
```

## 推奨される運用方針

### 原則：本人が承認者の場合は承認ステップをスキップし、次の上位者が承認する

この方式を推奨する理由：

#### 1. ガバナンス・牽制原則の観点
- 自己承認は不正抑止や公正性確保の観点から基本的に避けるべき
- 複数人による承認フローを維持することで、チェック機能が働く

#### 2. 運用の複雑化防止
- 自己承認を許可すると、承認フローが例外的ケースで煩雑化する
- 監査時の説明責任が増し、運用負荷が増加する

#### 3. 組織構造への適合
- 上長や上位者が承認することで、組織ガバナンス上のルールが明確に保たれる
- 一貫した承認フロー定義が可能になる

## 実装の詳細

### 承認フロー処理ロジック

申請者が承認者リストに含まれている場合の処理：

1. **本人の承認ステップをスキップ**  
   申請者と承認者が同じ場合、その承認ステップを検査対象から除外する

2. **次の承認者へ依頼**  
   次の承認者（通常は更に上位の者）に承認依頼を進める

3. **承認者がいない場合の特例対応**  
   申請者以外に承認者が存在しない場合のみ、特例として自己承認を許可する  
   （ただし、この場合は監査ログを必須とする）

### 承認フロー例

| ステップ | 承認者 | 申請者 | 処理                    | 説明                   |
|--------|--------|--------|----------------------|----------------------|
| 1      | 部長   | 部長   | **スキップ**           | 本人が承認者のため除外 |
| 2      | 本部長 | 部長   | **本部長が承認**        | 次の承認者に依頼      |
| 3      | 社長   | 部長   | 必要に応じて社長が承認 | 最終承認者が対応      |

## システム実装ガイドライン

### コード実装時の考慮点

```
申請者 == 承認者の場合：
  ├─ 承認ステップをスキップ
  └─ 次の承認者リスト要素へ処理を進める

次の承認者が存在しない場合：
  ├─ 特例フラグを立てる
  ├─ 監査ログに記録
  └─ 自己承認を許可
```

### 監査対応

- 自己承認が発生した場合、必ず監査ログに記録する
- ログには以下の情報を含める：
  - 申請ID
  - 申請者（兼承認者）
  - 承認日時
  - 「自己承認（特例）」フラグ

## 結論

- **原則**：本人承認はスキップ、上位者が承認する
- **例外**：次の承認者がいない場合のみ自己承認を許可（監査ログ必須）
- **効果**：ガバナンス強化、運用の単純化、公正性の確保
